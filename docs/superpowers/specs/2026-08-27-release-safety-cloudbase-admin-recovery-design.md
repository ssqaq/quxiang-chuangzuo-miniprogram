# 发布安全、CloudBase 直连核验与管理员异常恢复设计

## 1. 背景

当前项目存在一条微信开发者工具部署链和一条 CloudBase CLI 部署链。两条链路已经有部分版本、源码快照和云函数状态检查，但仍有以下风险：

1. GitHub 发布锁和云函数部署锁的默认路径按不同规则生成，多个发布入口可能没有共用同一把锁。
2. CloudBase CLI 可以完成上传和代码快照检查，但最终运行核验仍依赖微信开发者工具的管理员专用 `checkDeployment`。
3. 管理员页面对“服务不可用”和“没有管理员权限”的用户反馈边界不够稳定，服务异常时需要确保页面留在管理员页，并且可以重试恢复。
4. 当前工作区有大量其他任务的修改，发布同步不能使用全量暂存或全量复制，避免把无关改动一起发布。

本设计只处理发布安全、线上运行核验和管理员异常恢复，不改变普通用户生图、图片编辑、视频、换脸和记录业务。

## 2. 目标

- 所有真实发布入口默认使用同一套全局发布锁规则，并允许显式指定锁路径。
- 安全同步脚本只负责“当前工作区 → 发布 clone”的受控复制和校验。
- `sync-to-github.ps1` 继续负责版本升级、正式打包、提交和推送。
- CloudBase CLI 部署完成后可以直接做只读运行核验，不伪造管理员身份，不绕过权限。
- `-VerifyOnly` 可以在没有微信开发者工具的情况下完成 CloudBase 代码和运行状态核验。
- 管理员身份已经确认但服务异常时，页面显示服务异常、保留重试入口，不误报权限问题，不跳离管理员页。
- 所有专项检查、版本升级、正式打包和 GitHub 同步都能留下可复核结果。

## 3. 非目标

- 不把发布锁做成跨电脑的云端分布式锁。
- 不修改现有管理员专用 `checkDeployment` 的权限要求。
- 不把 API Key、SecretId、SecretKey、环境变量、完整服务器路径或用户数据写入日志、发布清单或同步目录。
- 不复制未列入 `IncludePath` 的文件。
- 不通过删除、重置或清理工作区来解决并行改动问题。
- 不在管理员服务异常时自动跳转首页、工作台或登录页。

## 4. 总体方案

```text
当前工作区
  ↓ 明确 IncludePath
安全同步脚本
  ↓ 复制前后 SHA256、存在性、大小校验
发布 clone
  ↓ 进入统一发布锁
sync-to-github.ps1
  ↓ 版本升级 → 预检查包 → 提交 → 正式打包 → 推送
GitHub
```

云函数部署和核验：

```text
取得统一部署锁
  ↓
记录 HEAD、版本和云函数源码快照
  ↓
本地依赖专项检查
  ↓
CloudBase CLI 或微信开发者工具上传
  ↓
等待云函数 Active
  ↓
CloudBase 代码快照核对
  ↓
只读运行健康核验
  ↓
再次核对本地源码快照
```

管理员页面：

```text
确认管理员身份
  ↓
读取统计模块
  ├─ 成功：显示数据
  ├─ 服务异常：显示“管理员服务暂时不可用”，保留重试
  ├─ 权限失败：显示权限提示
  └─ 单模块失败：只标记对应模块，不拖垮其他模块
```

## 5. 统一发布锁

### 5.1 公共锁模块

新增公共发布安全模块，集中负责：

- 默认锁路径计算；
- 显式锁路径解析；
- 独占文件句柄获取；
- 等待、超时和占用者信息读取；
- owner/pending 元数据写入；
- `finally` 路径释放锁和清理元数据。

默认路径不再由各脚本自行拼接不同文件名，而是由公共模块根据项目根目录和发布目标计算。GitHub 发布和云函数部署可以使用同一把发布锁，避免“代码正在同步时云函数同时上传”。

已有 `-DeployLockPath` 保留；`sync-to-github.ps1` 增加 `-LockPath`。显式路径优先于默认路径，便于测试和多项目隔离。

### 5.2 加锁范围

真实发布锁覆盖：

1. 读取远端状态；
2. 安全同步或受控文件准备；
3. 版本号读取和升级；
4. 依赖检查、专项测试和预检查打包；
5. 提交；
6. 正式打包；
7. 推送；
8. 云函数上传、线上核验和最后快照复查。

`VerifyOnly` 和只读检查不取得写发布锁，也不执行上传、版本修改、配置修改或日志写入。

### 5.3 并发和失败规则

- 锁被占用时按指定等待时间轮询，超时即失败；
- 未取得锁前不执行任何远程写操作；
- 进程异常退出时依靠操作系统释放文件句柄；
- owner 信息只记录 PID、开始时间、目标版本、目标类型和脱敏后的项目标识；
- 微信确认弹窗产生待确认任务时，保留 pending 占位，禁止其他发布覆盖；
- 任何版本、HEAD 或部署源码快照变化都终止当前发布，不把混合内容标记为成功。

## 6. 安全同步脚本

新增安全同步入口，职责限定为复制和校验：

```text
当前工作区 → 发布 clone
```

要求调用方明确指定：

- 源目录；
- 目标目录；
- 一个或多个 `IncludePath`。

### 6.1 复制范围

- 只复制 `IncludePath` 指定的文件或目录；
- 不修改源工作区；
- 不修改目标仓库未列出的文件；
- 不修改 Git index、暂存区、分支或提交；
- 不复制 `.env`、密钥文件、AppSecret、API Key 和临时文件；
- 目标路径必须解析在明确的发布 clone 内。

### 6.2 覆盖保护

复制前比较目标文件是否存在以及 SHA256：

- 目标不存在：允许创建；
- 目标存在且内容相同：记录为跳过；
- 目标存在但内容不同，且目标文件有用户改动：拒绝覆盖；
- 目标存在但内容不同，且已通过明确的受控发布规则确认：允许覆盖并记录原因。

脚本不通过模糊的“全量镜像”推断用户意图。

### 6.3 校验记录

每个复制项记录：

- 相对路径；
- 复制前后是否存在；
- 文件大小；
- SHA256；
- 创建、跳过或覆盖结果。

日志只使用仓库相对路径，不泄露用户目录、密钥和环境变量。

## 7. CloudBase 直接运行核验

### 7.1 只读运行动作

在 `cloudfunctions/api/index.js` 增加固定名称的只读运行健康动作，例如 `checkRuntimeHealth`。管理员专用 `checkDeployment` 保持原权限和业务语义不变。

运行健康动作只返回固定白名单字段：

```js
{
  ok: true,
  buildVersion: "0.49.x",
  buildMarker: "发布标记",
  runtime: {
    active: true,
    dependencies: {
      healthy: true,
      verified: ["jpeg-js", "pngjs", "wx-server-sdk", "xlsx", "local-modules"],
      failed: []
    }
  },
  checkedAt: "时间戳"
}
```

实际字段名以现有动作注册和部署脚本约定为准，但必须保持固定、脱敏、只读。

禁止返回：

- API Key、SecretId、SecretKey；
- 完整接口地址；
- 云函数服务器绝对路径；
- 环境变量原文；
- 用户标识和业务数据；
- 可由调用参数选择的任意配置项。

动作不得写数据库、部署日志或配置，不得触发迁移，不得调用计费型上游接口。

### 7.2 CloudBase CLI 数据流

1. 脚本从本地配置读取环境 ID、目标函数和期望版本。
2. 通过 CloudBase CLI 查询函数状态和代码快照。
3. 确认状态为 `Active`，版本、Build Marker、图片模式和超时符合预期。
4. 通过 CloudBase CLI 触发只读运行健康动作。
5. 解析返回的固定字段。
6. 断言依赖健康、失败列表为空、固定依赖全部已验证。
7. 核验失败时返回非零状态，并隐藏 CLI 原始输出。

CloudBase CLI 直部署和 `-VerifyOnly` 使用同一套断言。微信开发者工具部署链可以保留原有线上调用，但应尽量复用相同的结果校验函数，避免两套标准漂移。

### 7.3 失败分类

统一映射为可读错误：

- `FUNCTION_NOT_ACTIVE`：函数未处于 Active；
- `VERSION_MISMATCH`：线上版本和本次发布版本不一致；
- `BUILD_MARKER_MISMATCH`：构建标记不一致；
- `TIMEOUT_MISMATCH`：函数超时配置不一致；
- `RUNTIME_DEPENDENCY_UNHEALTHY`：运行依赖异常；
- `INVOKE_TIMEOUT`：只读动作调用超时；
- `INVOKE_ERROR`：CloudBase 调用失败；
- `MALFORMED_RESULT`：返回字段缺失或类型不正确。

错误信息只保留脱敏后的状态、字段名和依赖名，不打印原始响应。

## 8. 管理员服务异常专项测试

在现有 `scripts/admin-loading-smoke.js` 基础上增加页面级状态测试。测试使用 mock 服务，不连接真实 CloudBase，不写真实数据库。

### 8.1 核心场景

| 场景 | 预期 |
|---|---|
| 管理员身份成功，统计服务超时 | 显示服务不可用，可重试 |
| 管理员身份成功，服务返回 5xx | 显示服务不可用，不显示无权限 |
| 管理员身份成功，服务返回权限错误 | 显示权限提示 |
| 初次加载失败，点击重试成功 | 错误清除，数据恢复 |
| 重试仍失败 | 保留重试按钮，可再次点击 |
| 一个统计模块失败 | 其他模块继续显示 |
| 刷新期间重复点击 | 不产生并发重复加载，不破坏状态 |
| 服务异常期间调用跳转逻辑 | 不跳首页、工作台或登录页 |

### 8.2 必须断言

- `loading`、`refreshingAll` 和模块 loading 状态最终都能结束；
- 服务错误不会被归类为“没有管理员权限”；
- 失败模块拥有明确失败状态和 `canRetry`；
- 重试前进入 loading，重试后按成功或失败分别落状态；
- 成功后旧错误消息、失败标记和按钮状态被清理；
- 页面不调用 `wx.reLaunch` 离开管理员页；
- 日志能区分身份失败、权限失败、服务失败和数据格式失败；
- 失败模块不会覆盖其他模块已成功的数据。

### 8.3 测试替身

mock 服务按调用次数或场景返回：

1. 超时；
2. 服务错误；
3. 权限错误；
4. 成功数据。

测试要检查调用次数、页面 data、重试入口和跳转函数调用次数。测试结束后恢复原始模块加载器和全局微信对象，避免污染其他 smoke。

## 9. 版本、打包和同步

这是发布安全和管理员可用性修复，代码实现完成并通过专项测试后按补丁版本升级。当前发布 clone 记录的基线版本为 `0.49.0`；开发工作区可能处于更早版本，不能直接拿工作区版本覆盖发布版本。本次目标候选为：

```text
0.49.0 → 0.49.1
```

只有在发布锁内重新读取远端主线仍为 `0.49.0` 时，候选版本才是 `0.49.1`。如果实现过程中发现项目版本已经被其他受控发布任务升级，必须以远端最新版本为基线自动分配下一个补丁版本，不能覆盖已有版本。开发工作区的 `0.48.1` 只能作为待同步源码来源，不能作为最终发布版本依据。

交付顺序固定为：

1. 完成源码和脚本修改；
2. 运行 CloudBase 依赖、锁、同步、部署和管理员异常专项测试；
3. 在发布锁内读取并升级最新补丁版本；
4. 生成正式发布包并检查非空、大小和清单；
5. 按明确 `IncludePath` 使用安全同步脚本复制到发布 clone；
6. 由 `sync-to-github.ps1` 执行版本确认、正式打包、提交和推送；
7. 对 CloudBase 做真实部署或 `VerifyOnly` 核验；
8. 核对本地 `HEAD`、`origin/main` 和工作区状态；
9. 记录版本号、包路径、Git SHA、同步清单和核验结果。

任何正式打包失败、线上核验失败或同步校验失败，都不能报告为交付完成。

## 10. 回滚

- 安全同步发现目标有未授权改动时，停止复制，不删除目标文件；
- 发布脚本失败时保留本地提交和产物，不强制回滚工作区；
- CloudBase 核验失败时不继续 GitHub 正式同步；
- 线上已经上传但源码快照发生变化时，按最新源码重新部署，不把旧上传当作成功；
- 管理员页面异常时优先回滚到上一份已验证的小程序包和云函数版本；
- 回滚也必须使用统一发布锁、明确同步清单和完整线上核验。

## 11. 验收标准

### 发布安全

- GitHub 发布和云函数部署默认使用统一锁；
- 显式锁参数能够覆盖默认路径；
- 第二个写发布进程无法进入上传、提交或推送；
- 安全同步不会复制未列出的文件；
- 目标用户改动不会被静默覆盖；
- 同步前后 SHA256、存在性和大小校验通过。

### CloudBase

- CloudBase CLI 能完成直部署；
- 直部署后不依赖微信管理员页面即可完成运行核验；
- `VerifyOnly` 不上传、不修改配置、不写部署日志；
- 版本、Build Marker、Active、超时和运行依赖全部匹配；
- 健康动作不泄露敏感信息。

### 管理员页面

- 服务异常显示服务异常提示；
- 不误报无权限；
- 可重试；
- 重试成功后页面恢复；
- 单模块失败不拖垮整页；
- 不发生错误跳转。

### 交付

- 专项测试通过；
- 版本实际升级；
- 正式包存在且非空；
- GitHub 推送完成；
- 本地 `HEAD` 与 `origin/main` 一致；
- 工作区剩余改动均为用户或其他任务原有改动，不被本任务误提交。
