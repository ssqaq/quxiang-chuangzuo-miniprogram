# 版本并发发布处理设计

日期：2026-08-25

## 1. 背景

当前发布脚本已经有发布锁、暂存 tree SHA、提交前后工作区指纹和正式发布包校验，但版本号仍然直接从主工作区的 `config.js` 读取。

多个任务同时在主工作区准备发布时，可能出现以下问题：

- 两个任务都基于同一个旧版本号修改，最终产生相同的目标版本；
- 一个任务把另一个任务已经改好的版本文件一起暂存；
- 远端在打包或提交期间先进入新提交，当前任务仍然按旧版本继续发布；
- 发布失败后，工作区留下半套版本号，下一次发布继续误用。

本次改造只解决版本分配和发布过程的并发安全，不改变业务功能，不自动合并未列入本次发布的业务代码。

## 2. 目标与边界

### 2.1 目标

1. 在发布锁保护下，从 `origin/main` 的最新提交读取基础版本。
2. 自动分配下一个补丁版本，例如 `0.38.3` 自动得到 `0.38.4`。
3. 统一更新项目版本组，避免小程序、云函数和媒体服务版本不一致。
4. 远端在发布过程中变化时，自动丢弃本轮临时发布内容，重新读取远端版本并重试。
5. 当前工作区或未列入本次发布的并发修改不得被覆盖、不得被偷偷带入提交。
6. 发布成功后保留现有交付要求：正式 ZIP、发布记录、GitHub SHA 一致。

### 2.2 不在本次范围内

- 不自动合并两个任务对同一个业务文件的功能修改；
- 不解决云函数部署本身的线上灰度或回滚；
- 不把 API Key、AppSecret、`.env` 等敏感文件加入发布；
- 不改变现有 `IncludePath` 的显式文件范围约束。

## 3. 版本组

版本组由当前项目实际存在的发布组件组成。当前版本组为以下七个文件：

```text
config.js
cloudfunctions/api/index.js
cloudfunctions/api/package.json
cloudfunctions/api/package-lock.json
media-worker/package.json
media-worker/package-lock.json
cloudfunctions/watermark-gateway/package.json
```

只允许修改这些文件中的项目自身版本字段：

- `config.js`：`appVersion`
- `cloudfunctions/api/index.js`：`API_BUILD_VERSION`，同时生成新的构建标记
- 两个 `package.json`：顶层 `version`
- 两个 `package-lock.json`：根对象和 `packages[""]` 的 `version`
- `cloudfunctions/watermark-gateway/package.json`：顶层 `version`

依赖包的版本、业务代码、配置内容和锁文件中的其他字段不得被版本分配逻辑改写。

## 4. 推荐架构：临时发布工作树

不再直接使用当前脏工作区完成提交，而是在发布锁内创建一次性的临时发布工作树。

### 4.1 输入快照

进入发布流程后，先记录：

- 当前 `HEAD`；
- `origin/main`；
- `IncludePath` 文件内容和 SHA256；
- 当前工作区指纹；
- 发布尝试编号和进程信息。

发布过程结束前，若显式指定文件的内容或工作区指纹发生变化，立即停止，避免把并发修改混入本次发布。

### 4.2 创建临时发布工作树

每次尝试从最新 `origin/main` 创建临时 detached worktree：

1. 只把 `IncludePath` 明确指定的当前工作区文件复制到临时工作树；
2. 未列入 `IncludePath` 的业务文件全部使用远端基线；
3. 版本组中未列入 `IncludePath` 的文件使用远端基线，只做版本字段更新；
4. 版本组中列入 `IncludePath` 的文件保留当前任务的功能修改，再只改版本字段。

这样既能自动补齐版本组，又不会把其他任务对未列入文件的修改带进来。

### 4.3 自动分配版本

每次尝试都从临时工作树的远端基线读取 `config.js.appVersion`，只允许合法的三段式语义版本：

```text
主版本.次版本.补丁版本
```

目标版本固定为：

```text
主版本.次版本.补丁版本 + 1
```

例如：

```text
0.38.3 -> 0.38.4
```

不自动跨次版本或主版本，不接受工作区手填版本覆盖远端版本。

### 4.4 版本预留记录

每次尝试在仓库外的发布预留目录写入临时记录，至少包含：

```json
{
  "baseHead": "远端基线 SHA",
  "targetVersion": "0.38.4",
  "attempt": 1,
  "pid": 1234,
  "createdAt": "2026-08-25T00:00:00.000Z",
  "includePaths": ["pages/example/example.js"]
}
```

预留记录只用于审计和故障恢复，不进入 Git，不作为远端版本的唯一锁。远端快进推送成功才算真正占用版本；失败或结束后删除临时预留记录。

## 5. 冲突与重试

### 5.1 本机发布锁

现有发布锁改为有限等待，而不是发现占用就立即失败：

- 默认最多等待 60 秒；
- 每 250 毫秒检查一次；
- 超时后明确报告占用锁的路径和当前进程信息。

### 5.2 远端变化

每次尝试都执行以下检查：

1. 创建临时工作树前 fetch；
2. 记录 `origin/main` 作为 `baseHead`；
3. 预打包前核对远端仍为 `baseHead`；
4. 提交后推送时使用快进推送；
5. 推送被拒绝或远端 SHA 变化时，清理临时工作树，重新 fetch，重新分配下一个补丁版本。

默认最多重试 3 次。每次重试都重新生成版本预留记录和发布包，不复用旧版本包。

### 5.3 工作区变化

远端变化可以自动重试；本地工作区变化不能盲目重试：

- 显式 `IncludePath` 内容变化：停止并提示调用方重新开始；
- 未列入 `IncludePath` 的文件变化：不纳入本次发布，但在最终状态中保留；
- 发布锁、临时 worktree、预留记录和临时 ZIP 必须在失败路径清理。

## 6. 提交与当前主工作区

提交在临时发布工作树完成，主工作区不执行覆盖式 checkout。

推送成功后：

1. 确认远端 SHA 等于最终提交 SHA；
2. 仅当当前主分支引用仍然等于本次 `baseHead` 时，安全快进本地主分支引用；
3. 当前工作区文件保持原样，不覆盖并发任务的未提交内容；
4. 若无法安全移动本地主分支引用，发布仍判定为成功，但交付报告明确提示需要在干净工作树执行一次 fast-forward。

已有的发布记录继续写入：

```text
D:\aips小程序\wechat-miniapp-release-records\release-v版本-提交号.json
```

记录中增加：

- `baseHead`
- `targetVersion`
- `attempt`
- `retryCount`
- `generatedVersionPaths`
- `releaseWorktree`

## 7. 错误处理

所有失败路径都必须：

1. 不推送未通过正式打包的提交；
2. 删除临时 worktree；
3. 删除临时版本预留记录；
4. 保留原主工作区内容；
5. 输出可以直接执行的下一步。

错误信息至少区分：

- 发布锁超时；
- 本地工作区在流程中变化；
- 远端在流程中变化且已重试；
- 版本字段格式非法；
- 版本组文件缺失；
- 发布包校验失败；
- 推送重试达到上限。

## 8. 测试方案

新增 `scripts/version-concurrency-smoke.js`，使用临时 Git 仓库和本地 bare remote 验证：

1. 基线 `0.38.3` 发布后自动生成 `0.38.4`；
2. 第二次发布自动生成 `0.38.5`；
3. 远端抢先提交时，第一次推送失败，第二次尝试读取新基线并生成下一补丁版本；
4. 本地 `IncludePath` 文件在流程中被修改时，发布停止且原文件内容不变；
5. 未列入 `IncludePath` 的并发业务文件不会进入提交；
6. 七个版本组文件最终版本完全一致；
7. 失败后无残留临时 worktree、预留记录和空 ZIP。

保留并继续执行：

```powershell
node scripts/release-safety-smoke.js
node scripts/validate.js
```

正式发布仍必须通过 `scripts/package-release.py` 生成非空 ZIP，并核对 ZIP 完整性、版本、commit SHA、tree SHA 和源码指纹。

## 9. 交付验收标准

- 连续两个发布不会得到相同补丁版本；
- 远端并发提交不会造成错误版本提交；
- 未列入本次发布的并发代码没有进入提交或发布包；
- 失败重试不会污染主工作区；
- `HEAD` 与 `origin/main` 最终一致，或报告明确说明无法安全快进的原因；
- 发布包、发布记录和 GitHub 提交三者版本与 SHA 一致。
