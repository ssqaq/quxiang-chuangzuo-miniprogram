# 云函数依赖实测与并行部署保护设计

## 背景

当前主线版本为 `0.46.2`。现有 `scripts/deploy-and-verify-api.ps1` 已经会在部署前运行项目检查，并在部署后真实调用线上 `checkDeployment`，因此能发现部分云函数启动失败。

但现有流程仍有两个缺口：

1. 没有系统检查 `cloudfunctions/api/package.json` 中声明的全部 npm 依赖、本地 `file:` 依赖和源码里的相对 `require()` 文件是否完整；
2. GitHub 同步已有独占发布锁，但云函数部署没有独占锁，多个任务同时部署时可能后上传的旧目录覆盖先上传的新目录。

本设计同时解决这两个问题，不改变普通生图、腾讯版换脸、照片转实况和制作记录的业务流程。

## 目标

- 部署前自动扫描 `cloudfunctions/api` 的依赖完整性。
- 所有静态相对 `require()` 都必须能解析到真实文件或目录入口。
- `package.json` 中全部 `dependencies` 都必须能在本地加载。
- `file:` 本地依赖必须位于云函数目录内，且包入口文件完整。
- 部署后的 `checkDeployment` 返回脱敏的运行依赖健康状态。
- 部署脚本必须断言线上依赖健康，否则本次部署判定失败。
- 同一台电脑同一时间只允许一个写部署流程运行。
- `-VerifyOnly` 保持纯只读，不抢写锁，也不修改线上配置。
- 部署期间如果 Git HEAD、版本号或云函数源码发生变化，立即终止，不能把混合版本判定为成功。
- 所有检查和锁状态不得输出密钥、环境变量、服务器绝对路径或用户数据。

## 非目标

- 不引入云数据库分布式锁。
- 不阻止开发者正常编辑源码；只在发现部署期间源码变化时终止部署。
- 不替代微信开发者工具和 CloudBase 自身的函数状态检查。
- 不扫描运行时动态拼接出来的模块名；动态依赖必须显式加入检查清单。
- 不修改现有 GitHub 发布锁和受控同步规则。
- 不复制或移动腾讯 SecretId、SecretKey。
- 微信开发者工具确认弹窗不可用时，允许使用已登录的 CloudBase CLI 走同一套锁和快照保护。

## 方案总览

```text
开始写部署
  ↓
取得本机独占云函数部署锁
  ↓
记录 Git HEAD、版本号、云函数源码指纹
  ↓
运行项目检查 + 云函数依赖完整性检查
  ↓
再次确认源码快照未变化
  ↓
上传云函数并远程安装 npm 依赖
  ↓
等待云函数 Active
  ↓
核对线上版本、Build Marker、超时和运行依赖健康状态
  ↓
再次确认本地源码快照未变化
  ↓
释放部署锁
```

只读核验流程：

```text
VerifyOnly
  ↓
不获取写部署锁
  ↓
不上传代码、不修改超时、不写部署日志
  ↓
核对线上代码快照和运行依赖健康状态
```

## 本地依赖完整性检查

新增：

```text
scripts/check-cloudfunction-dependencies.js
```

默认检查：

```text
cloudfunctions/api
```

### package.json 依赖

脚本读取 `dependencies`，逐项执行等价于 Node `require.resolve()` 的解析，并检查：

- 包能从云函数目录解析；
- 包入口文件存在；
- 包可以被 `require()` 加载；
- `package-lock.json` 存在；
- lock 文件的根依赖声明与 `package.json` 一致。

Node 内置模块不属于 `dependencies`，不要求写入 `package.json`。

### file: 本地依赖

对 `file:` 依赖额外检查：

- 目标路径必须位于 `cloudfunctions/api` 内；
- 目标目录和 `package.json` 必须存在；
- `main` 指向的入口文件必须存在；
- 当前的 `file:vendor/xlsx` 必须能解析和加载；
- 不允许通过 `../` 引用云函数目录外的文件，避免本地能用、上传后丢失。

### 相对 require

递归扫描云函数源码中的静态调用：

```js
require("./lib/example")
require("../shared/example")
```

每个相对引用必须按 Node 规则解析到：

- 同名文件；
- `.js` 或 `.json` 文件；
- 目录下的 `package.json` 入口；
- 目录下的 `index.js` 或 `index.json`。

扫描范围包括云函数入口、`lib` 和测试引用到的云函数源码；排除 `node_modules`、`.git` 和无需扫描的打包产物目录。

无法静态判断的动态 `require()` 会列为错误，除非在脚本中的明确白名单登记。

### 输出

成功时只输出数量和依赖名称，例如：

```text
依赖检查通过：4 个 npm 依赖、18 个相对模块、0 个缺失文件
```

失败时输出仓库相对路径和缺失模块名，不输出电脑用户名、云环境变量和密钥。

## 线上运行依赖探针

扩展 `cloudfunctions/api/index.js` 的 `checkDeployment` 返回：

```js
{
  runtimeDependencies: {
    healthy: true,
    verified: [
      "jpeg-js",
      "pngjs",
      "wx-server-sdk",
      "xlsx",
      "local-modules"
    ],
    failed: []
  }
}
```

约束：

- 只返回固定的依赖名称和健康布尔值；
- 不返回 `require.resolve()` 得到的服务器路径；
- 不返回包内容、环境变量、密钥和错误堆栈；
- 失败原因只保留脱敏错误码和依赖名称；
- `checkDeployment` 的管理员权限和 `readOnly` 行为保持不变。

云函数入口本身已经加载核心依赖；探针再对固定清单做显式检查，确保线上返回可以被发布脚本稳定断言。

## 部署脚本强制断言

`scripts/deploy-and-verify-api.ps1` 在普通部署前新增：

```text
node scripts/check-cloudfunction-dependencies.js
```

部署后和 `-VerifyOnly` 模式都必须检查：

```text
runtimeDependencies.healthy === true
failed.length === 0
```

并确认固定依赖名称全部存在。任意一项不满足时：

- 脚本返回非零退出码；
- 不显示部署成功；
- 保留清楚但脱敏的错误提示；
- 不继续 GitHub 正式同步。

## 独占云函数部署锁

锁文件位于项目目录外：

```text
D:\aips小程序\wechat-miniapp-cloud-deploy.lock
```

所有真实写部署使用 `.NET FileStream` 和：

```text
FileShare.None
```

持有整个流程，直到线上核验和本地快照复查全部结束。

同时写入可读的占用信息文件：

```text
D:\aips小程序\wechat-miniapp-cloud-deploy.lock.owner.json
```

只记录：

- 进程 PID；
- 开始时间；
- 本地 Git HEAD；
- 目标版本；
- 云函数名称；
- 项目目录。

不记录任何密钥和环境变量。

### 抢锁规则

- 普通部署默认等待最多 60 秒；
- 每秒尝试一次；
- 超时后显示占用 PID、开始时间和目标版本；
- 拿不到锁时不运行任何上传或线上写操作；
- 持锁进程退出后由 `finally` 关闭句柄并清理占用信息；
- 进程异常退出后操作系统自动释放文件句柄，后续任务可以重新取得锁；
- `-VerifyOnly` 和 `-DryRun` 不获取写部署锁。

### 微信确认弹窗

微信开发者工具可能把云函数写操作返回为 `pending + taskId`，要求在开发者工具内确认。此时：

- 保存脱敏的待确认任务记录；
- 释放当前进程文件锁，但保留待确认记录作为跨进程发布占位；
- 新的普通部署看到待确认记录后必须停止，禁止重复上传；
- 用户确认后使用 `-ResumePendingDeploy` 查询并继续同一个 taskId；
- 只有旧任务明确成功后才继续线上核验；
- 旧任务失败、取消或过期后才清理占位并允许重新部署；
- 待确认记录不保存密钥、环境变量或上传文件内容。

### CloudBase CLI 兜底

如果微信开发者工具的确认窗口无法正常操作，使用：

```text
scripts/deploy-api-cloudbase-cli.ps1
```

这个入口不绕过安全检查，仍然会：

- 取得同一个独占部署锁；
- 执行本地依赖检查；
- 使用 `--install-dependency true` 远程安装依赖；
- 上传后复查云函数源码快照；
- 不打印 CLI 原始输出，避免意外带出敏感配置。

## 部署期间源码快照

取得锁后记录：

- `git rev-parse HEAD`；
- `config.js` 中的 `appVersion`；
- `cloudfunctions/api` 内所有部署文件的相对路径、大小和 SHA256；
- `package.json`、`package-lock.json`、`config.json` 和入口文件必须包含在指纹中。

在以下节点重新核对：

1. 本地检查完成、上传开始前；
2. 上传完成、线上核验开始前；
3. 线上核验成功、释放锁前。

任一节点发现变化立即停止并提示具体变化的仓库相对路径。线上可能已经完成上传时，也不能把本次发布标为成功，必须由最新源码重新部署和验证。

## 测试

### 依赖检查专项测试

新增测试覆盖：

- 当前真实 API 云函数依赖检查通过；
- 缺少 `package.json` 依赖时失败；
- npm 包入口缺失时失败；
- `file:` 目录缺失时失败；
- `file:` 依赖越出云函数目录时失败；
- 相对 `require()` 文件缺失时失败；
- 目录入口和 `.json` 模块能正确解析；
- 输出中不出现绝对用户目录和环境变量。

测试使用临时目录，不删除或移动真实云函数依赖。

### 部署锁专项测试

部署脚本 smoke 覆盖：

- 普通部署会取得独占锁；
- 第二个写部署进程在锁被占用时不能进入上传步骤；
- 第一个进程释放后第二个可以取得锁；
- 异常路径仍会释放锁；
- `-VerifyOnly` 不等待写部署锁；
- `-DryRun` 不创建写部署锁；
- 部署前后会比较 HEAD、版本和云函数源码指纹。

### 线上验收

- 云函数状态为 `Active`；
- 线上版本、Build Marker 与本地一致；
- 超时为 900 秒；
- `runtimeDependencies.healthy` 为 `true`；
- 固定 npm 依赖和本地模块均显示已验证；
- 普通生图配置仍是原配置；
- 腾讯版仍是 `GPT Image 2 → FuseFaceUltra` 两阶段；
- `-VerifyOnly` 不写部署日志、不上传代码、不修改配置。

## 版本与发布

这是发布安全修复，版本按补丁升级：

```text
0.46.2 → 0.46.3
```

交付顺序：

1. 完成代码和专项测试；
2. 升级小程序和云函数版本、Build Marker；
3. 运行完整项目检查；
4. 生成正式发布包；
5. 使用带独占锁的新脚本部署 API 云函数；
6. 运行线上只读核验；
7. 通过受控同步脚本提交并推送 GitHub；
8. 核对本地 HEAD 与 `origin/main` 一致；
9. 生成并检查 `0.46.3` 真机预览二维码。

## 回滚

如果新依赖检查或部署锁导致发布流程异常：

- 业务云函数代码无需回滚，普通用户调用不受脚本本身影响；
- 可以回滚本次脚本、测试和 `checkDeployment` 返回字段；
- 使用上一版正式包恢复 `0.46.2`；
- 回滚部署仍必须单进程执行，避免再次发生并行覆盖。

## 已知边界

- 本机文件锁只能阻止同一台电脑上使用本脚本的并行部署，不能阻止另一台电脑或控制台手工上传。
- 源码快照能发现部署期间本地文件变化，但无法撤回已经完成的线上上传；因此发现变化后必须重新部署最新版本。
- 如果云函数缺少入口阶段必需依赖，函数会在运行探针前启动失败；本地完整性检查和部署后的真实调用共同负责抓住这种情况。
